Foundations

01 · Lessons 1 and 7

Agentic coding vs vibe coding

What
Two ways of building with AI. Vibe coding hands the decisions to the AI. Agentic coding keeps the decisions with you and uses AI agents to do the work.
Why
Vibe coding is fast but unpredictable. On real systems you need code you understand, can review, and can trace back to a requirement.
When
Vibe code prototypes, hackathons and throwaway MVPs. Use agentic workflows for anything with users, money or data on the line.

Vibe coding goes like this: you type "build me an auth system", the AI writes a lot of code, you click around, you say "no, not like that", and you loop until it seems to work. It's great for exploring an idea. The problem is that the AI quietly makes dozens of decisions for you. Which framework? JWT or sessions? What are the password rules? What happens after three wrong passwords? If it guesses wrong, you find out late, and you end up in a loop of patches on code you never really understood.

Agentic coding flips the control. You decide the important things up front (usually in a written spec), and the agent executes. It reads the codebase, plans, edits files, runs commands and tests, and reports back. You review at checkpoints. It is slower to start, but the output is consistent, traceable, and fits production code.

AspectVibe codingAgentic / spec-driven
Starting pointA rough idea in one promptA written spec with clear requirements
Who decidesThe AI guessesYou decide, the AI implements
SpeedVery fast to first outputSlower start, fewer rewrites
Code qualityUnpredictableConsistent and traceable to the spec
Debugging"It's broken, fix it"Compare output against the spec
Typical failureCode nobody understandsOver-engineering (watch for it)
Do you need to know how to code?Not reallyYes. You are leading the AI.
✕ Vibe prompt
Build me a user authentication system.
✓ Agentic prompt
Add email + password registration to this Flask app.
- Use the existing users table in @database/db.py
- Hash passwords with werkzeug.security
- Server-side validation: all fields required,
  password == confirm, email unique
- On success: flash message, redirect to /login
- Don't add new dependencies. Don't touch other routes.

Why the second one works: every decision the AI would otherwise guess (library, validation, redirect, scope) is already made. The agent spends its effort on implementation, not on inventing requirements.

  • Learn the fundamentals of your language and framework first. Agentic coding amplifies what you already know. It doesn't replace it.
  • Treat every output like a pull request from a new teammate: read it, run it, question it.
  • Keep Git in the loop from day one. Branches and small commits are your undo button.
02 · Lesson 2

Setup and your first session

What
Installing Claude Code, logging in, opening it inside a project, and asking the right first questions.
Why
A clean setup (project folder, Git repo, virtualenv) makes every later workflow smoother.
When
Once per machine, and the first few minutes on any new or unfamiliar repo.

Install and log in

Claude Code runs in your terminal and needs a paid Claude plan (Pro or higher) or an Anthropic API/Console account. Install it with the official script, then run claude inside your project folder.

# macOS / Linux / WSL
curl -fsSL https://claude.ai/install.sh | bash

# Windows PowerShell
irm https://claude.ai/install.ps1 | iex

# Then, from your project root
cd ~/code/invoice-api
claude

The first time, it asks whether you trust the folder (say yes for your own code) and opens a browser to authorize your account. You can use Claude Code from the terminal, the VS Code / JetBrains extensions, the desktop app, or the web. The terminal is the most complete: a few features (editing memory, configuring hooks) still work best there.

Bash mode: run shell commands inside the session

Type ! at the start of the input to switch to bash mode and run a shell command without leaving Claude Code. The command and its output become part of the conversation, so you can follow up with "why did that fail?" or "what did that install?". If you run the same command in a separate terminal, Claude never sees it.

! python3 -m venv .venv
! source .venv/bin/activate
! pip install -r requirements.txt
! python3 app.py
> The server started on 5001 but /login returns 500. Look at the traceback above and explain the cause.
TipBash output costs context tokens too. Use ! for commands whose output Claude should reason about. For noisy things (a 3,000-line install log, a dev server that streams forever), use a separate terminal.

Put the project under Git first

git init
git add . && git commit -m "Initial commit"
git remote add origin git@github.com:you/invoice-api.git
git push -u origin main

The three questions to ask on any new repo

Before changing anything, get oriented. These three prompts give you (and Claude) a map of the project.

What does this project do? Summarize what is implemented today and what looks unfinished.
What tech stack does this project use? List backend, frontend, database, testing and deployment tools, with the files that prove each one.
Explain the project structure as a tree. For each important folder, say what belongs there and what should not.

Running it for free (with limits)

If you can't pay yet, you can point Claude Code at open-source models through Ollama. You get the same interface, but a weaker model: expect slower responses and lower quality, especially on local models with limited RAM. Ollama's hosted "cloud" models have usage caps that a few big requests can burn through.

# after installing Ollama
ollama pull qwen2.5-coder:7b      # a local coding model (fits ~16 GB RAM)
ollama launch claude              # pick a cloud or local model from the menu
Be realisticFree setups are fine for learning the interface. For real projects, and for the workflows in this guide (plan mode, subagents, long refactors), the quality gap with Anthropic's models is large.
03 · Lessons 3 and 14

How Claude Code actually works

What
A "coding harness": software wrapped around a Claude model that gives it tools (read, write, bash, search), memory and safety checks.
Why
Once you see the loop, you understand why context fills up, why permissions exist, and where hooks and subagents fit.
When
Read this once. It makes every later topic easier.

Think of the model as the brain and the harness as the body. The model (Opus, Sonnet or Haiku) runs on Anthropic's servers and only produces text. It can't open a file. The harness running on your machine does everything else: it sends your prompt plus context to the model, reads the model's reply, and when the reply says "call the Read tool on app.py", the harness actually opens the file and sends the contents back.

That back-and-forth is the agent loop. One prompt usually triggers many turns:

youPrompt"Add a DELETE /expenses/<id> endpoint"
model → toolRead app.pyHarness opens the file, returns contents
model → toolRead schema.sqlChecks the table structure
model → toolEdit app.pyYou approve the diff
model → toolBash: pytestRuns tests, returns output
modelDoneSummary back to you. Loop ends.

Two consequences matter for everything else in this guide:

  • Everything in the loop costs tokens. File contents, command output and the model's replies all go into the context window, and the whole conversation is sent again on each turn.
  • The model is probabilistic, the harness is deterministic. The model can misread an instruction, especially deep into a long session. The harness does exactly what it's told. That's why Claude Code asks permission before risky tools, and why hooks exist.

Tools and permissions

Built-in tools include Read, Write/Edit, Bash, Grep/Glob (search), WebSearch/WebFetch and Agent (starts subagents). You can add more with MCP. In Manual mode, Claude asks before editing files or running commands. Use /permissions to allow, ask or deny specific tools so you aren't clicking "yes" 40 times a session.

{
  "permissions": {
    "allow": [
      "Bash(pytest:*)",
      "Bash(git status)",
      "Bash(git diff:*)",
      "WebSearch"
    ],
    "ask":  [ "Bash(git push:*)" ],
    "deny": [ "Read(./.env)", "Read(./secrets/**)", "Bash(rm -rf:*)" ]
  }
}
Where the rule livesApplies toCommitted to Git?
.claude/settings.local.jsonOnly you, only this projectNo
.claude/settings.jsonEveryone working on this repoYes
~/.claude/settings.jsonYou, in every projectNo

Permission modes

A permission mode decides what Claude may do without asking you first. Recent versions start in auto mode. Press Shift+Tab to switch: the cycle runs Manual → accept edits → plan, then back to auto when it's available.

ModeRuns without askingBest for
AutoEverything, while a second model (a classifier) checks each action in the backgroundLong tasks, fewer prompts
Manual (default in settings)Only reads. Asks before edits and commands.Sensitive work, reviewing every step
Accept editsReads, file edits and common file commands (mkdir, mv, cp)Iterating on code you're watching
PlanRead-only research and planning. No edits.Exploring before a change

Your deny rules apply in every mode, including auto. That's why the .env and rm -rf rules above are worth setting even if you rarely see a permission prompt.

  • Allow safe, read-only or test commands. Keep anything that pushes, deletes, deploys or touches secrets on "ask" or "deny".
  • Deny reading .env and credential files outright. It also keeps them out of your context window.
  • Watch the diff Claude shows before you approve an edit. Red lines go, green lines come in. It takes seconds and catches most surprises.
04 · Lesson 3

Sessions and built-in slash commands

What
A session is one conversation, from claude to /exit. Slash commands are shortcuts that trigger a built-in action without writing a prompt.
Why
Good session habits keep context clean and make work resumable. Commands save typing and expose settings, usage and memory.
When
All day, every day. Type / to see the full list with descriptions.

Session habits that pay off

  • One feature per session. Start fresh for each feature so unrelated context doesn't pile up.
  • Rename right away with /rename login-flow. The auto-generated name comes from your first question and is rarely useful later.
  • Resume instead of re-explaining. claude -c continues the last session. claude -r (or /resume inside a session) shows a picker.
  • Commit at every milestone inside a session. Small commits make it easy to roll back one bad step.
  • Ask side questions with /btw. The answer appears in an overlay and is not added to the conversation, so your main context stays clean.
  • Export important sessions with /export notes/auth-refactor.md before a big refactor, so you can feed a summary back later.
> /rename payment-retries
> Implement exponential backoff for failed Stripe charges in @billing/retry.py
> /btw what's the difference between idempotency keys and retries in Stripe?
  (answer shows in an overlay · press space to dismiss · not saved to context)

05 · Lesson 4

Prompting and making code changes

What
How to ask for edits so Claude touches the right files, stays in scope, and matches your design.
Why
Vague prompts make Claude search, guess and over-edit, which costs tokens and review time.
When
Small to medium changes you can describe in one message. Bigger work belongs in a spec and plan.

Point at files with @

Type @ and pick a file or folder. This removes the guesswork ("which footer?") and saves Claude from searching. Without it, Claude may find a different file than you meant, or create a new one.

Say what not to touch

A single line like "Don't change anything else" is one of the most useful constraints you can add. It stops helpful-but-unwanted refactors.

✕ Vague
Add terms and privacy links to the footer and make pages for them.
✓ Specific
Add two plain text links to the footer in @templates/base.html:
"Terms and Conditions" → /terms and "Privacy Policy" → /privacy.

Then add both routes to @app.py and create templates/terms.html
and templates/privacy.html with generic content for a personal
expense-tracking app. Match the existing styles in
@static/css/style.css. Don't change anything else.

Why: exact file paths, exact link text and routes, a reference for styling, and a scope fence. Claude reads four files instead of exploring the project, and you get one clean diff.

Turn a design into code with an image

Claude's models are multimodal. Paste a screenshot or mockup (Ctrl+V in the terminal, or drag the file in) and describe exactly which part to build.

[pasted image: hero-v2.png]
Rebuild only the hero section in @templates/landing.html and @static/css/landing.css to match this image: centered headline, two buttons, the illustration on the right, and a "See how it works" link. Reuse the existing color variables. Don't touch any other part of the page.
Real mistake from the courseThe prompt named a CSS file that didn't exist, so Claude created a second stylesheet next to the real one. Always double-check paths you type, or use @ autocomplete so a typo can't slip in.

Write the prompt before you open the terminal

For anything beyond a one-liner, draft the prompt in a notes file first (or have a chat assistant tighten it), then paste it in. You'll forget fewer requirements, and you can reuse the good ones.

Add a "See how it works" modal to @templates/landing.html.
Requirements:
- Clicking the button opens an overlay with an embedded YouTube video (use a placeholder URL for now)
- Close on the X button, on clicking outside, and on Escape
- When the modal closes, the video must stop playing
- Vanilla JavaScript only. No new libraries.
- Don't modify any other part of the project.
  • Iterate inside the same session. "The spacing is too large on mobile, reduce the padding in the hero only" is cheaper than starting over.
  • Commit after each change that works. git add -p plus a clear message takes a few seconds and saves hours.
  • Simple, one-shot edits are fine like this. For features with several moving parts, move to the spec and plan workflow.

Context and memory

The two ideas that separate power users from everyone else: how the context window fills up, and how to give Claude persistent knowledge of your project without repeating yourself.

06 · Lesson 5

The context window

What
The model's working memory: everything it can see at once, measured in tokens. Usually around 200K for Claude Code.
Why
It drives cost, it limits how long a session can run, and answer quality drops as it fills up.
When
Always. Check /context during any long session.

Context is everything needed to understand a task: your code, the spec, tickets, team chat, earlier messages. The context window is the maximum amount of that the model can hold at once. You can't drop a million-line codebase into it and ask anything.

Here is what you need to know about how Claude Code uses it:

  • Each new session starts with a fresh window. Nothing from the previous session is in it unless it comes from a file like CLAUDE.md.
  • Both sides count. Your prompts, pasted code and images are input tokens. Claude's replies, the files it reads and every tool output also land in the window. Output from Claude and its tools usually fills the window much faster than what you type.
  • The model has no memory, so the whole conversation is re-sent on every turn. Turn 10 carries turns 1–9 with it. Long sessions get expensive fast.
  • Not all 200K is yours. The system prompt, tool definitions, MCP tools, CLAUDE.md, memory and skill descriptions load before you type, and a buffer is held back for auto-compaction. In practice you have roughly 150K to work with.
  • Quality drops as it fills. Deep into a full window, Claude is more likely to forget instructions or miss details in the middle of the conversation.

Auto-compact, /compact and /clear

When usage gets high, Claude Code auto-compacts: it summarizes the conversation so far and replaces the history with that summary. It keeps you going, but it can happen in the middle of a task, and a summary always loses detail.

So do it yourself, at a moment you choose. Check /context. When you are around 60–70% full and between tasks, run /compact, optionally telling it what to keep. Press Ctrl+O afterwards to read the summary.

> /context
  ⛁ Messages 88.4k · System 6.3k · Tools 8.3k · MCP 3.9k · Memory 1.2k · Free 58k
> /compact Keep the final schema for the invoices table, the list of files changed, and the two failing tests. Drop the exploration.
SituationDo this

Big exploration or research neededHand it to a subagent. It has its own window and returns a short summary.

Keep junk out of the window

Big generated files (lock files, build output, virtualenvs, data dumps, minified bundles) should never be read. The reliable way is a deny rule in .claude/settings.json. (Some guides mention a .claudeignore file, but it was never reliably honored. Use permission rules instead.)

{
  "permissions": {
    "deny": [
      "Read(./.venv/**)", "Read(./node_modules/**)", "Read(./dist/**)",
      "Read(./data/raw/**)", "Read(./**/*.min.js)", "Read(./package-lock.json)"
    ]
  }
}
  • One feature, one session. Four features in one session costs several times more than four separate sessions, because every turn re-sends everything before it.
  • Compact proactively, not in the middle of an important change.
  • Write focused, specific prompts. Vague prompts make Claude read more files to figure out what you mean.
  • Use subagents for isolated or exploratory work so the main window only gets the conclusion.
07 · Lesson 6

CLAUDE.md, the .claude folder and memory

What
A markdown file Claude loads at the start of every session: your project's standing instructions. Think of it as a persistent system prompt.
Why
Without it, you re-explain your stack, commands and conventions every session, and you'll forget something.
When
Set it up on day one of any project, then keep it current.

Create it

Run /init. Claude scans high-signal files (package.json, requirements.txt, README, config), the folder tree and naming patterns, then writes a starter CLAUDE.md in the project root. Treat that as maybe 30% of the job. The valuable part (workflows, constraints, what to avoid) only you know. Edit it, then commit it.

What goes in a good CLAUDE.md

# Spendly: personal expense tracker

Flask + SQLite web app. Users register, log expenses in INR, and see
spending summaries on a profile page.

## Architecture
- app.py            routes only, no SQL here
- database/db.py    all SQL (get_db, init_db, seed_db, query helpers)
- templates/        Jinja2, every page extends base.html
- static/css/       vanilla CSS, variables in style.css

## Code style
- Type hints on all Python functions
- Functions under ~40 lines; extract helpers
- Parameterized SQL only (never f-strings in queries)

## Tech constraints
- Flask only, no ORM, no JS frameworks, no new dependencies without asking
- Currency is INR (₹). Dates are YYYY-MM-DD. Timezone is IST.

## Commands
- Install: pip install -r requirements.txt
- Run:     python3 app.py   (port 5001)
- Test:    pytest -q

## Roadmap
| Step | Feature                 | Status |
| 01   | Database setup          | done   |
| 02   | Registration            | done   |
| 03   | Login / logout          | in progress |
| 04   | Profile page            | todo   |

## Never do this
- IMPORTANT: never delete or recreate spendly.db
- Don't edit .env or anything in migrations/ without asking

The roadmap section is a trick from the course: listing features with a status column gives Claude a sense of what's done and what's next, so every session behaves more consistently.

Where CLAUDE.md files can live

LocationScopeLoaded
./CLAUDE.md or ./.claude/CLAUDE.mdProject, shared with the team via GitEvery session
./CLAUDE.local.mdYour personal notes for this project, git-ignoredEvery session
~/.claude/CLAUDE.mdYou, across all projects (your style, preferred tools)Every session

The .claude folder: Claude Code's toolbox

your-project/ ├── CLAUDE.md ├── CLAUDE.local.md # personal, git-ignored └── .claude/ # project level, committed ├── settings.json # permissions + hooks for the team ├── settings.local.json # your personal overrides ├── rules/ # CLAUDE.md split by topic ├── commands/ # custom slash commands (legacy format) ├── skills/ # skills, one folder each ├── agents/ # custom subagents └── specs/ # your own convention for spec docs ~/.claude/ # user level, never committed ├── CLAUDE.md, settings.json, commands/, skills/, agents/ └── projects/<project>/memory/MEMORY.md # auto memory

Keep it short: under ~200 lines

Every line of CLAUDE.md is loaded in every session, and instruction-following gets worse as the instruction count grows. For each line, ask: would Claude make mistakes if I deleted this? If not, delete it. When a large project outgrows 200 lines, you have three options:

  • Split into .claude/rules/: code-style.md, testing.md, security.md. Easier to maintain, and a rule file can declare paths: in its frontmatter so it only loads when Claude works on matching files.
  • Import other files with @docs/api-guidelines.md on its own line in CLAUDE.md.
  • Add folder-level CLAUDE.md files for frontend, backend and database code in a monorepo.
Use IMPORTANT sparinglyWriting IMPORTANT or MUST in front of a rule makes Claude weigh it more. If ten lines say IMPORTANT, none of them stand out. Save it for the two or three rules that would hurt if broken.

Auto memory

Separately from CLAUDE.md (which you write), Claude keeps its own notes as it works: patterns, preferences, corrections. They are saved to ~/.claude/projects/<project>/memory/MEMORY.md and loaded at the start of each session (the first 200 lines). Open everything with /memory: project memory, user memory, and the auto-memory folder.

You can also write to it directly at the end of a useful session:

Update your memory with what we learned this session: amounts are stored in paise as integers, the profile page date filter uses inclusive ranges, and tests must use the in-memory SQLite fixture from tests/conftest.py.
  • Treat CLAUDE.md as a living document. After each feature, add what's new and delete what's stale. Commit the changes.
  • When Claude makes the same mistake twice, don't just correct it. Say "add this rule to CLAUDE.md" so it sticks.
  • Only put rules that apply across the whole project in CLAUDE.md. Feature-specific details belong in that feature's spec.
  • Audit it monthly. Old instructions drift and can start contradicting the code.

08 · Lessons 7–9

Spec-driven development

What
Write a spec (the why and what) before any code. The spec becomes the single source of truth that planning, coding and testing all follow.
Why
It removes the guessing that causes rework, and gives you something concrete to validate against.
When
Any feature with more than one moving part: new endpoints, auth, data model changes, integrations.

The full loop

1Branchfeature/… off fresh main
2SpecWhy and what. No tech choices.
3 · youReview specFix gaps before any code
4PlanThe how: plan mode writes it
5 · youReview planFiles, order, risks
6ImplementTask by task
7Test + reviewSeparate agents
8 · youValidateAgainst acceptance criteria
9ShipCommit, PR, merge, clean up

What a spec contains

Keep the spec free of technology choices. It describes behavior, so it survives a change of stack. The how goes into the technical plan.

# 03 · Login and logout

## Problem
Registered users can't sign in, so no personalized page can exist yet.

## Functional requirements
- GET /login shows the form; POST /login validates email + password
- On success store user_id in the session and redirect to /profile
- GET /logout clears the session and redirects to /
- Logged-in users visiting /login or /register are redirected to /profile

## Input / output
- Input: email, password (form POST)
- Output: redirect on success, re-rendered form with a flash error on failure

## Constraints
- Reuse the users table and helpers in database/db.py
- No new dependencies. Parameterized SQL only.

## Edge cases
- Unknown email and wrong password show the SAME generic error
- Empty fields are rejected server-side, not just in HTML

## Acceptance criteria
- [ ] Valid credentials log in and land on /profile
- [ ] Wrong password shows "Invalid email or password"
- [ ] /logout clears the session
- [ ] Logged-in user cannot reach /login or /register
Spec vs planThe spec says what and why (often written with product people). The technical plan says how: data model, endpoints, files to change, order of work. Keeping them separate means one spec can drive a Flask plan today and a FastAPI plan next year.

Generate specs instead of hand-writing them

Writing specs by hand is good practice the first few times. After that, a custom command drafts them from your codebase and CLAUDE.md, and you review. (You'll build this command in section 10.)

/create-spec 05 csv-export
Users should be able to download their expenses as CSV, filtered by the same date range as the profile page.
  • Read every generated spec. The course's login spec missed "logged-in users shouldn't see /login", and it was only caught during manual testing. One extra line in the spec would have prevented it.
  • Store specs in the repo (.claude/specs/) and number them. They double as documentation of how the app grew.
  • Validate against the acceptance criteria at the end. It is the fastest way to see if the feature is actually done.
  • Watch for over-engineering. A clear spec sometimes gets an elaborate implementation. Ask Claude to simplify when the diff is bigger than the feature.
09 · Lesson 8

Plan mode, extended thinking and effort

What
A read-only mode where Claude explores the code and writes an implementation plan, but can't edit anything until you approve.
Why
Finding a wrong assumption in a plan costs one message. Finding it in 400 lines of code costs a rewrite.
When

Skills

Models are good generalists but mediocre at your version of a specialized task: your company's slide layout, your frontend design system, your code-review checklist, your way of doing exploratory data analysis. Pasting a giant prompt every time is error-prone. Putting it in the system prompt burns context in every session, even when unused. Prompts also can't bundle files, are hard to share and version, and don't compose.

A skill fixes all of that. It's a folder with a SKILL.md file (required) plus any scripts, templates or reference files it needs.

.claude/skills/ └── frontend-design/ ├── SKILL.md # required: frontmatter + instructions ├── templates/ # reference layouts, component snippets └── scripts/ # helpers the skill can run
---
name: spendly-ui-designer
description: Use when building or restyling any Spendly page or component
  (templates/*.html, static/css). Applies the Spendly design system.
---
# Spendly UI

## Rules
- Jinja2 + vanilla CSS only. Extend base.html. Use variables from style.css.
- Cards: 12px radius, 1px border var(--line), no drop shadows.
- Money: right-aligned, tabular numbers, "₹1,24,500" Indian grouping.
- Every table gets an empty state ("No expenses in this range yet").

## Before finishing
- Check the page at 375px width. No horizontal scroll.
- See templates/card.html for the stat card pattern.

Progressive disclosure is what makes skills cheap. At session start only each skill's name and description are loaded. When your request matches a description, Claude loads the SKILL.md body. If the body points to a script or template, that is read only when needed. So you can have twenty skills and pay for twenty short descriptions.

Three ways to get a skill

  • Use the skill-creator skill (recommended for your first ones). Describe what the skill does, when it should trigger, and what good output looks like. It asks follow-up questions and writes SKILL.md for you.

Subagents: built-in and custom

What
Helper agents the main agent starts, each with its own fresh context window, prompt, tools and model. They do a job and return only a summary.
Why
Heavy reading stays out of your main context. You get specialists, unbiased reviewers, and parallel work.
When
Codebase exploration, testing, code and security review, multi-stage pipelines, independent tasks that can run in parallel.

The problem they solve

Say the codebase is 30K tokens and each turn adds about 5K of new messages and tool output. Without a subagent, "analyze the code and plan auth" loads those 30K into your main window, and they're re-sent on every later turn: turn 1 carries ~35K, turn 4 ~50K, and turn 8 ~70K (leaving the startup load aside). With a subagent, the 30K are read in a separate window, a ~500-token plan comes back, and the separate window is thrown away. Turn 8 then carries ~40K instead of ~70K: every turn is about 29.5K lighter. Long windows also suffer from being "lost in the middle": models attend less to the middle of a very long context.

Built-in subagents

AgentUsed for
ExploreRead-only codebase search and summarizing. Triggered automatically when you ask Claude to explore or understand code.
PlanResearch that feeds a plan in plan mode.
General-purposeMulti-step tasks that need both reading and writing.

Claude starts these on its own (implicit), or you can ask directly (explicit):

Use an Explore subagent to map how authentication works across this repo (middleware, session storage, decorators, tests). Return a one-page summary with file paths. Don't paste file contents back.

Custom subagents

A built-in agent does a generic security review. A custom one follows your checklist. Create one with /agents → Create new agent (let Claude draft it, then edit), or write the file yourself in .claude/agents/.

---
name: security-reviewer
description: Reviews changed code for security issues. Use after a feature
  is implemented and before it is committed.
tools: Read, Grep, Glob, Bash(git diff:*)
model: opus
color: yellow
---
You are a senior application security reviewer for a Flask + SQLite app.

Review only the files changed on this branch (git diff main...HEAD).
Check, in order:
1. SQL built with f-strings or string concatenation (must be parameterized)
2. Routes missing the login_required check
3. User A able to read or edit user B's rows (missing user_id filter)
4. Secrets, keys or tokens in code or templates
5. Unescaped user input in templates (|safe on user data)

Output a table: severity · file:line · issue · fix.
End with a verdict: APPROVE or CHANGES REQUESTED. Do not edit files.

Frontmatter options include name, description (how Claude decides when to use it), tools, model, color, and more (skills, hooks, memory, effort). Give each agent only the tools it needs. A reviewer doesn't need Write.

Two pipelines worth copying

Testing (sequential). /test-feature <spec> runs a test-writer agent (writes pytest tests from the spec, not from the code, because the code might be wrong), then a test-runner agent (read-only, runs them and reports pass/fail with root causes). Writer and runner are separate so neither grades its own homework.

Review (parallel). /review-feature <spec> starts a security-reviewer and a quality-reviewer at the same time. They're independent, so they run in parallel, and the main agent merges their findings into one report and asks before fixing anything.

---
description: Run security and quality review in parallel for a feature
argument-hint: <spec-name>
---
Spec: .claude/specs/$ARGUMENTS.md

1. In parallel, launch the security-reviewer and quality-reviewer subagents.
   Give each the spec path and tell them to review `git diff main...HEAD`.
2. Merge both reports into one table sorted by severity. Remove duplicates.
3. Give an overall verdict. List the changes you recommend.
4. Ask me before applying any fix.
Parallel agents need separate filesThree agents editing the same file at once works, but the main agent then has to untangle their edits. Split parallel work by file or module: auth service, payments service, user service. Not three sections of one template.
  • Code written by one agent is reviewed better by a different agent. The writer carries its own assumptions and blind spots.
  • Keep subagent output short. Ask for a summary, a table or a verdict, not file dumps. Whatever it returns lands in your main context.
  • Subagents are not free. Each one reads files in its own window. Use them where isolation pays off, not for a two-file change.

Hooks

What
Your own scripts that the harness runs automatically at specific events: before a tool runs, after an edit, when Claude stops, when a session starts.
Why
CLAUDE.md rules are followed most of the time. Hooks run every time. They add determinism to a probabilistic system.
When
Anything that must always happen (format, lint) or must never happen (delete the DB, edit .env).

Recall the brain-and-body picture. The model is a slightly moody boss. The harness is an obedient employee that does whatever the model asks. If, deep in a long refactor, the model decides rm spendly.db is "cleanup", the harness will do it. "Never delete the database" in CLAUDE.md works maybe 98% of the time. Hooks cover the other 2%.

Hooks attach to events in the session lifecycle. The ones you'll use most:

EventFiresTypical use
SessionStartSession begins or resumesInject a status summary, recent commits, open TODOs
UserPromptSubmitYou send a promptAdd context, block prompts containing secrets
PreToolUseBefore a tool runsBlock dangerous commands, protect files
PostToolUseAfter a tool succeedsFormat and lint edited files
NotificationClaude needs your inputDesktop or phone alert
Stop / SubagentStopClaude (or a subagent) finishes"Done" notification, run the test suite
PreCompactBefore compactionSave a transcript or notes first
SessionEndSession closesLog, clean up temp files

Anatomy of a hook

Hooks live in settings.json (project, local or user). Each has an event, an optional matcher (which tools it applies to, like Bash or Write|Edit), and an action (the command to run). The harness pipes a JSON description of the event to your script on stdin. Your script's exit code decides what happens: 0 means continue, 2 means block, and whatever you print to stderr is sent back to Claude so it can change course.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "python3 .claude/hooks/block_dangerous.py" }]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [{ "type": "command",
                    "command": "jq -r '.tool_input.file_path' | grep '\\.py$' | xargs -r black -q" }]
      }
    ],
    "Stop": [
      { "hooks": [{ "type": "command",
                    "command": "curl -s -d 'Claude finished in spendly' ntfy.sh/your-topic >/dev/null" }] }
    ]
  }
}
import json, re, sys

event = json.load(sys.stdin)
cmd = event.get("tool_input", {}).get("command", "")

PROTECTED = ["spendly.db", ".env", "migrations/"]
DANGEROUS = [r"\brm\b", r"\bmv\b", r">\s*\S", r"\btruncate\b", r"DROP\s+TABLE"]

if any(p in cmd for p in PROTECTED) and any(re.search(d, cmd, re.I) for d in DANGEROUS):
    print(f"Blocked: '{cmd}' touches a protected file. Ask the user to do this manually.",
          file=sys.stderr)
    sys.exit(2)   # block the tool call, send the message to Claude

sys.exit(0)       # allow

Tested in the course: asked to "delete spendly.db", Claude tried rm spendly.db, the hook blocked it, and Claude replied that a safety rule prevents the deletion and the user would have to do it manually.

Popular hook ideas

  • Auto-format (Black, Prettier, gofmt) after every edit, so code written across ten sessions looks like one person wrote it.
  • Lint (Ruff, ESLint) after edits to catch unused imports, undefined names, unreachable code and bare except: before anything runs.
  • Block dangerous shell commands and protect sensitive files (.env, DB files, migrations, CI config).
  • Notify your phone or desktop when a long task finishes, so you can work elsewhere.
  • Session-start briefing: print git log --oneline -10 and a progress file. Output from a SessionStart hook is added to Claude's context.
  • Telemetry: log subagent start/stop events to a dashboard to see how work is distributed.
Hooks run with your permissionsA hook is a shell command that runs automatically. Review hooks from others as carefully as any script you'd run, and set up protective hooks at the start of a project, not after an accident.

✓ Optimized
Before we stop: write .claude/handoff.md with what was built, files changed, decisions made, open issues, and next steps. Under 40 lines.

[new session]
Read @.claude/handoff.md. Continue with "next steps" item 1.

Why it's better: a 40-line handoff carries what matters in maybe 1K tokens. The old session carried 140K, much of it dead ends. The new session also starts at full answer quality.

✕ Inefficient
[keeps going until auto-compact fires in the middle of a migration]
✓ Optimized

Why it's better: you pick the moment (between steps) and what survives. Auto-compact picks for you, and the summary may lose the detail you need next.

9. Send exploration to a subagent

✕ Inefficient
Read all the files in src/ and explain how the notification system works.
✓ Optimized
Use a subagent to explore how notifications are sent (queues, providers, retries, templates). Return a summary under 300 words with the key file paths. Don't paste code.

Why it's better: the subagent may read 40K tokens of code, but only the ~500-token summary enters your main context, and that's all the later turns carry.

10. Ask for less output

✕ Inefficient
Update the validation and show me the complete updated file with a detailed explanation of every change.
✓ Optimized
Update the email validation in @lib/validators.ts to reject plus-addressing for admin accounts. Make the edit, then reply with a one-line summary.

Why it's better: the diff is already visible in the approval prompt. Reprinting the whole file and narrating it doubles the output and stays in the history for the rest of the session.

11. Batch related small edits

✕ Inefficient
Rename getUser to fetchUser.
[turn] Also update the imports.
[turn] Oh, and the tests.
[turn] And the docs mention it too.
✓ Optimized
Rename getUser → fetchUser everywhere: definition, imports, tests and docs/. Run the type checker and tests when done.

Why it's better: four turns re-send the history four times. One complete instruction does it once.

12. Trim command output before it reaches Claude

✕ Inefficient
! npm test
✓ Optimized
! npm test -- --silent 2>&1 | tail -40
! pytest -q -x --no-header

Why it's better: a full verbose test run can be thousands of lines. The failures at the end are what matter.

17.4

Agentic workflow patterns

Spec → Plan → Build → Verify

  • Spec states what and why
  • Plan mode writes the how
  • Implement task by task
  • Validate against acceptance criteria

Writer / Reviewer split

  • One agent writes the code
  • A different agent reviews it
  • Removes the writer's blind spots

Test writer → Test runner

  • Writer tests the spec, not the code
  • Read-only runner executes and reports
  • Sequential: runner needs the writer's output

Parallel fan-out

  • Independent tasks, separate files
  • One subagent per task
  • Main agent integrates and runs the suite

Explore → Summarize

  • Subagent reads the heavy stuff
  • Returns a short summary with paths
  • Main context stays small

Plan with Opus, build with Sonnet

  • Strongest model for reasoning
  • Balanced model for execution
  • Haiku for mechanical edits
17.5

Context management

Every session

  • One feature or task per session
  • /rename it right away
  • Check /context in long sessions
  • Side questions go in /btw

When it fills up

  • ~60–70%: /compact with focus notes, between steps
  • Task done: /clear or a new session
  • Too deep: write a handoff, start fresh

Keep it lean

  • CLAUDE.md under ~200 lines
  • Few MCP servers and plugins
  • Deny reads of build output, deps, data
  • Skills over giant prompts

Signs you're too deep

  • Claude forgets rules from CLAUDE.md
  • Repeats a mistake you already corrected
  • Answers get slower and vaguer
  • Auto-compact fires
17.6

Planning

Use plan mode for

  • Changes across several files
  • Refactors and migrations
  • Unfamiliar parts of the codebase
  • Anything you can't describe in two sentences

A good plan lists

  • Files to change or create
  • Order of work, tests green at each step
  • Data model and API changes
  • Risks and open questions
  • How each acceptance criterion is verified

Tuning

  • /model Opus for hard plans
  • Thinking on (/config)
  • /effort medium to high
  • /ultraplan when regular plans are shallow

After the plan

  • Save it to a file
  • Review it (or get a second opinion)
  • Implement in a fresh session from the file
17.7

Debugging

Give Claude

  • Exact error and stack trace (trimmed)
  • Expected vs actual behavior
  • Steps to reproduce
  • What changed recently (commit, deploy)
  • The likely files, with @

Ask for

  • Ranked hypotheses before fixes
  • A cheap experiment per hypothesis
  • A failing test that reproduces it
  • The smallest fix, then the full suite

Techniques

  • Temporary logs tagged for cleanup
  • git bisect with Claude running the check
  • Paste a screenshot for UI bugs
  • Use ! so errors land in context

Avoid

  • "It's broken, fix it"
  • Accepting a fix without a root cause
  • Letting it edit tests to pass
  • Debugging deep in a bloated session
17.8

Code review

Review checklist

  • Matches the spec and acceptance criteria
  • Edge cases and error handling
  • Security: injection, authz, secrets, XSS
  • Performance: N+1 queries, unbounded work
  • Readability, naming, dead code
  • Tests cover the new behavior

Set up once

  • security-reviewer agent (read-only, Opus)
  • quality-reviewer agent (read-only)
  • /review-feature runs both in parallel
  • Ask before applying fixes
17.9

Common mistakes

Workflow

  • Building several features in one session
  • Skipping the spec, then fixing guesses for hours
  • Not reading the plan before approving
  • No branch, no commits: nothing to roll back to
  • Trusting "all tests pass" without looking

Prompts

  • Vague asks that force repo-wide searches
  • Typos in file paths (use @)
  • Pasting whole logs and files
  • No "don't change anything else"
  • Re-explaining the stack every session

Setup

  • Connecting every MCP server you find
  • A 500-line CLAUDE.md, with IMPORTANT everywhere
  • Installing community skills without reading them
  • Allowing rm, git push or deploys without asking

Security

  • Tokens pasted into prompts or screenshots
  • Claude allowed to read .env
  • Write access to a production database
  • Over-scoped GitHub tokens
